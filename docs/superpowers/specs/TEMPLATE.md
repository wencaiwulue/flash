# <Subsystem Name>

本文是对当前实现的回溯性设计说明，不冒充原始历史设计记录。

> 使用要求：正文必须让读者不读全部源码，也能理解主要入口、状态、控制流、失败路径和设计取舍。不要用“负责管理”“提高可靠性”“保证一致性”等抽象句代替具体机制。每项关键设计决策都要回答：实际行为是什么、为什么这样设计、备选方案是什么、付出了什么代价、证据在哪里。

## 1. 问题与约束

必须包含：

- 一个具体的失败场景或需求冲突，说明没有当前设计时会发生什么。
- 子系统的调用方、被调用方和责任边界。
- 实际平台、协议、兼容性、安全、性能或 feature flag 约束。
- internal/external、CLI/SDK 或 offline/live 差异；没有差异时明确说明。

推荐结构：

```text
当 <具体输入或故障> 发生时，<调用方> 需要 <可观察结果>。
如果 <备选行为>，会导致 <具体错误、数据丢失或状态不一致>。
因此本子系统必须在 <约束> 下完成 <职责>。
```

避免：只写“代码缺少文档”“系统很复杂”“需要提高可维护性”。

## 2. 设计理由与备选方案

至少覆盖所有影响公共契约、状态所有权、持久化、并发、安全和失败语义的主要决策。每项使用以下结构：

| 决策 | 实际机制 | 为什么采用 | 备选方案及不采用原因 | 代价 | 证据 |
|---|---|---|---|---|---|
| <具体决策> | <符号、数据结构或执行顺序> | <由约束推导出的理由> | <真正可行的备选及其失败场景> | <复杂度、延迟、兼容性等> | <路径+符号；或“设计推断”> |

证据规则：

- 源码注释、公开 contract、schema、协议和已评审设计可直接支持动机。
- 只有代码结构时，可以描述当前效果，但历史动机必须写“**设计推断：……**”。
- 不得从 commit 标题、文件名或测试名称虚构历史原因。
- 不要把“更简单”“更可靠”作为完整理由；说明对谁更简单、在哪条路径更可靠。

## 3. 目标与非目标

目标必须是当前实现实际承担的可观察职责，不是未来愿望。非目标必须列出容易被误认为属于本 spec 的相邻职责，并指出负责它们的 spec 或模块。

推荐分为：

- **状态与生命周期**：本模块拥有什么，不拥有什么。
- **接口与数据**：本模块保证哪些输入输出，不保证哪些格式或兼容性。
- **执行与环境**：支持哪些入口和构建条件，不支持哪些平台/live 路径。
- **依赖边界**：哪些职责由上游/下游 spec 解释，本文只描述调用关系。

## 4. 架构、模块与数据流

### 4.1 入口与公共契约

用 TypeScript 或等价表格写出关键入口、重要参数、返回类型和副作用：


解释调用方如何进入、实现如何返回、哪些依赖是注入的，以及异步 generator、Promise、回调或共享状态的完成条件。

### 4.2 模块与状态所有权

|---|---|---|---|---|

### 4.3 主控制流

画出至少一条端到端控制流，并在每一步写输入、输出和状态变化：

```text
调用方输入
  → 入口：验证/规范化什么
  → 状态所有者：写入什么
  → 核心执行：产生什么消息或副作用
  → 持久化/外部调用：等待还是后台执行，为什么
  → 最终结果：成功、失败和提前返回分别是什么
```

若存在循环、并发、恢复或短路径，要分别画出分支条件，不能只画成功路径。

### 4.4 数据结构与持久化

列出关键数据结构、身份关联和顺序约束，例如 UUID、parentUuid、消息类型、队列、快照、缓存、锁和 lease。说明：

- 数据在内存、文件或外部服务中的格式。
- 写入等待策略及其对恢复和延迟的影响。
- 恢复时如何重建链、缓存和状态。
- 哪些字段不能持久化、记录日志或暴露给调用方。

### 4.5 跨子系统依赖

列出上游输入、下游副作用和相关 spec。引用其他模块时说明“本文描述调用契约，主设计由哪个 spec 负责”，不要复制对方正文。

## 6. 现状验收标准

验收标准必须能独立判断行为是否满足设计，并与第 4、5 章一一对应。每项写：

1. 给定什么初始状态和输入。
2. 执行哪个入口或场景。
3. 必须观察到什么消息、状态、文件或清理结果。
4. 哪些副作用绝不能发生。

示例形式：

```text
当 <故障或输入> 发生在 <阶段> 时，系统必须 <具体行为>，
并且 <资源/消息/持久化状态> 必须 <不变量>；不得 <禁止副作用>。
```

不要写“测试通过”“构建成功”作为子系统行为验收，也不要把历史执行结果写进 spec。实际命令输出只进入 STATUS 或验证记录。

## 9. 改进建议

每条建议都必须能追溯到具体代码或已记录的验证边界，不得写成泛泛的重构愿望。使用以下结构：

| 优先级 | 触发场景与证据 | 建议方向 | 回归风险 | 验收方式 | 工作量 | 置信度 |
|---|---|---|---|---|---|---|
| P0–P3 | <何时出现问题+路径/符号> | <改变哪个契约或路径> | <可能破坏什么> | <如何判断改进有效> | S/M/L | 已证实/待运行验证/设计推断 |

分级约束：

- **P0**：已确认的安全、数据丢失、核心正确性或协议边界问题，必须有直接证据。
- **P1**：高影响可靠性、生命周期、并发、性能或显著耦合；不能只依赖推测。
- **P2**：局部可维护性、重复实现、测试缺口和有边界的重构。
- **P3**：可选体验、命名、风格和低收益优化，明确非紧急。

建议方向不是实施承诺。本次文档工作不顺便修改产品代码。
