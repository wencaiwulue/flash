# 以日期和功能命名全部 commit 的设计与实施文档

## 1. 背景

项目早期的 `docs/specs/<short-sha>-SPEC.md` 和 `docs/plans/<short-sha>-PLAN.md` 主要由提交标题、diff 统计和通用 fallback 拼接而成。它们能够证明文件存在，却不能说明方案设计，也不能指导实施。

当前基线 `c69c271db2278642918bce5caf9641108e4f6cab` 已把文档改造成结构化记录，并补充了前置状态、架构、设计决策和文件级步骤。本次不推倒重做这些内容，而是解决剩余的两个问题：

1. 交付文档仍以 SHA 命名，不能从文件名直接识别日期和功能。
2. 文档包含历史 CI、命令执行和 live 验证结果；本次要求只保留验收标准，不追踪或声明历史执行结果。

## 2. 范围

设计确认时的内容基线包含 **94 个 commit**。每个 commit 均有独立的 SPEC 和 PLAN，另保留一对 `self` 文档承接尚未形成最终 SHA 的当前工作。仅按这个静态基线计算，生成物为 **190 份 SPEC/PLAN**，另有 `INDEX.md` 和 `docs/status/index.json`。

本设计文档的评审提交以及后续实施提交也属于当前工作。执行 `--next` 时，当前 HEAD 必须有对应的历史记录，不能继续把它当作设计确认时的 `self` 而遗漏。最终数量必须由生成时的 Git 历史动态计算，不能把 94 或 190 写成固定校验值；新提交沿用现有 `self` 机制，避免为了记录自身 SHA 而递归修改提交。

### 目标

- 用 `YYYY-MM-DD + 功能名` 命名全部历史 SPEC/PLAN。
- 保留每个文档与完整 commit SHA 的精确对应关系。
- 保留现有实质性设计、文件/符号引用和文件级实施步骤。
- 从历史 SPEC/PLAN 中移除验证证据、历史 CI 结果和执行通过声明。
- 让命名、覆盖、链接、空泛正文和过期生成物成为自动检查项。
- 保持生成与检查分离，CI 只执行只读检查。

### 非目标

- 不改写 Git 历史、commit message 或产品实现。
- 不重新执行历史提交对应的测试、CI、OAuth、Cloud 或桌面验证。
- 不把回溯重建的 PLAN 表述为提交当时保存的原始计划。
- 不为追求篇幅给 rename、元数据迁移等提交虚构产品架构或数据流。
- 不保留旧 SHA 文档副本或承诺旧深链继续有效；仓库内链接必须全部迁移。

## 3. 文档内容契约

### 3.1 SPEC

每份 SPEC 包含：

1. **前置状态与问题**：父提交中的相关实现和本次要解决的问题。
2. **目标与非目标**：限定行为范围和明确不处理的事项。
3. **方案架构与数据流**：模块职责、控制流、数据流或元数据迁移过程；纯元数据提交描述真实的记录变化，不强行套产品架构。
4. **文件、接口与复用关系**：变更文件、复用模块、测试文件及其设计作用，必要时标注符号和 revision。
5. **关键决策与工程取舍**：解释为何采用实际实现，以及回溯可见的备选方案。
6. **安全与协议边界**：权限、凭据、生命周期、兼容性和协议约束。
7. **验收标准**：可判断实现是否符合设计的行为条件，不记录历史执行结果。
8. **实现状态与剩余范围**：说明实现边界，不把实现状态等同于环境验证结果。

SPEC 和 PLAN 均保留回溯性说明：内容依据对应提交的 diff、该 revision 的实现与测试重建，不冒充历史原文。

### 3.2 PLAN

每份 PLAN 包含：

1. 目标、前置条件和需要复用的现有实现。
2. 兼容、迁移和生命周期约束。
3. 按依赖排序的文件级实施步骤；每一步说明具体改动和涉及路径。
4. 风险及处理方式。
5. **验收顺序**：以应然语义说明先检查什么、再检查什么，不声明这些检查历史上已经执行或通过。
6. 已完成实现和剩余工作，仅用于描述代码范围，不附历史测试结论。

### 3.3 历史执行信息的处理

删除结构化记录中的 `evidence` 数据及渲染器的“验证证据”章节。正文也不能借其他章节保留“某次 CI 已通过”“本地实际执行成功”或 run ID 等历史结果。

代码行为可以保留。例如，“脚本成功时输出 `SKILLHUB_LIVE_OK`”是设计行为；“实际运行返回 `SKILLHUB_LIVE_OK`”是历史执行结论，本次不保留后者。

对于本身就是状态或证据文档更新的 commit，只说明文档结构、状态迁移、修改位置及其影响，不复述测试、CI 或 live 执行结果。

## 4. 文件命名设计

### 4.1 输出格式

历史文档采用：

```text
docs/specs/YYYY-MM-DD-<feature-slug>-SPEC.md
docs/plans/YYYY-MM-DD-<feature-slug>-PLAN.md
```

例如：

```text
docs/specs/2026-11-11-live-validation-workflows-SPEC.md
docs/plans/2026-11-11-live-validation-workflows-PLAN.md
```

`self` 不是历史 commit，继续使用：

```text
docs/specs/self-SPEC.md
docs/plans/self-PLAN.md
```

内部 `scripts/commit-docs/records/<short-sha>.ts` 文件名不变。它们是按 SHA 加载的数据记录，不是交付文档；每条记录通过新增的 `slug` 支持最终输出命名。

### 4.2 日期和 slug

- 日期取 Git committer date 的 ISO 日期部分，即现有 `%cI` 值的前 10 个字符，保留提交自带时区对应的自然日。
- `slug` 是每条记录显式维护的功能名，不从 commit subject 自动翻译或猜测。
- slug 使用小写英文 kebab-case，匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`。
- `self` 在创建时也必须提供 slug，使其后续固化为历史记录时无需补猜功能名。

### 4.3 同日同功能冲突

按 Git 历史和提交顺序处理同一 `YYYY-MM-DD/<slug>`：

- 第一次不追加序号。
- 第二次追加 `-02`，第三次追加 `-03`，依此类推。
- 序号位于 `-SPEC.md` 或 `-PLAN.md` 之前，SPEC 和 PLAN 使用相同 basename。
- 如果追加序号后仍与其他 slug 形成的输出路径冲突，校验失败并要求调整 slug，不静默覆盖。

例如：

```text
2026-11-11-finalize-commit-docs-SPEC.md
2026-11-11-finalize-commit-docs-02-SPEC.md
```

## 5. 组件设计

### 5.1 记录层：`schema.ts` 与 `records/`

- `CommitRecord` 新增必填 `slug`。
- 删除 `CommitEvidence`、`EvidenceKind` 和 `CommitRecord.evidence`。
- `ReferenceRole` 删除仅服务于执行证据来源的 `evidence` 角色，保留 `changed`、`reused` 和 `test`。
- `plan.verification` 重命名为 `plan.acceptanceSequence`，使数据契约与“只写验收标准”一致。
- `CommitKind` 中的 `evidence-update` 仅表示该历史提交的类型，不表示新文档继续保存执行证据。

### 5.2 命名层：独立模块

新增单一职责的命名模块，负责：

- 从 commit date 提取自然日。
- 校验 slug 格式。
- 按历史顺序分配同日序号。
- 为 SPEC 和 PLAN 生成一致路径。
- 检测最终路径冲突。

渲染器不各自拼接文件名，索引和文档清单必须复用同一命名结果。

### 5.3 加载与校验层

加载和校验继续采用失败即报错的方式：

- 缺少记录、SHA 不匹配、缺少 slug 或 slug 非法时失败。
- 运行时记录仍带遗留 `evidence` 属性、`plan.verification` 属性或 `evidence` 引用角色时失败，不能仅依赖 TypeScript 类型检查发现问题。
- 普通变更文件必须被设计引用或变更分组覆盖。
- changed/reused/test 引用及符号必须存在于声明的 revision。
- rename 必须有正确的 old/new 配对。
- PLAN 步骤路径必须已声明，顺序由记录显式维护。
- 通用 fallback、空章节、占位符、敏感信息和跨记录复制正文继续失败。
- 生成清单中出现重复路径、错误序号或过期命名时失败。

自动检查证明结构和引用满足契约，不宣称能够证明设计语义正确。

### 5.4 渲染层：`render.ts`

渲染器只把审核后的记录投影为 Markdown，不创作技术正文：

- SPEC 不再输出“验证证据”。
- PLAN 输出“验收顺序”，数据来源为 `acceptanceSequence`。
- frontmatter 继续保存完整 SHA、标题、日期、状态和 kind。
- `INDEX.md` 输出新文档链接，并保留 SHA 作为查找键。
- `docs/status/index.json` 同时保存 full SHA、日期、功能 slug、SPEC 路径和 PLAN 路径。

### 5.5 写入与检查入口

`document-commits.ts` 继续作为唯一写入口，`check-commit-docs.ts` 只读比较：

- `--next` 用于当前工作，覆盖当前 HEAD 和 `self`。
- 默认 head 模式用于提交后，覆盖全部祖先和 `self`。
- writer 不负责隐式删除旧文件；迁移旧文件是显式、可审查的操作。
- checker 将缺失、过期和孤儿 SPEC/PLAN 都作为失败报告。
- CI 不调用 writer，避免先重写再检查而掩盖遗漏。

## 6. 数据流

```text
Git 历史（SHA、日期、parent、diff）
                  │
                  ▼
显式结构化记录（slug、设计、引用、步骤、验收）
                  │
                  ▼
记录/引用/命名/质量校验 ───── 失败：停止，不生成替代正文
                  │ 成功
                  ▼
统一命名与渲染
          ┌───────┼────────┐
          ▼       ▼        ▼
        SPEC     PLAN    INDEX + JSON
          └───────┼────────┘
                  ▼
只读 checker 比较磁盘文件并发现孤儿
```

完整 SHA 是记录和索引的稳定身份；日期+slug 只是人类可读的输出名称。重命名输出文件不改变记录与 commit 的绑定方式。

## 7. 迁移设计

1. 将当前 `self` 中描述 `c69c271` 的内容固化为该 SHA 的历史记录；为设计文档评审提交等已经落地的当前工作分别建立历史记录，再创建代表后续实施的 `self`，保持 head/next 清单语义一致。
2. 为所有历史记录补充人工确认的 slug，并移除执行证据字段及正文中的历史结果表述。
3. 先让命名和渲染测试覆盖代表性记录，再执行全量 `--next` 生成。
4. 对照 Git 清单确认新 SPEC/PLAN 数量、日期、slug、序号和 SHA 映射。
5. 更新仓库内文档链接、模板和维护政策，再显式移除旧 SHA 命名的生成物。
6. 使用只读 checker 确认没有旧文件、孤儿、断链或未更新生成物；重复生成不得产生差异。

旧文件必须在新文件和索引完整之后移除。若迁移中断，仓库可能暂时同时存在新旧文件，但 checker 必须失败，不能把中间状态视为完成。

## 8. 错误处理

| 错误 | 处理 |
|---|---|
| 缺少记录或 slug | 报告对应 SHA 和字段，停止生成 |
| slug 格式错误 | 指出记录文件，不接受自动修复 |
| 同日同 slug | 按历史顺序分配稳定序号 |
| 序号后仍发生路径冲突 | 报告冲突路径和两个来源，停止生成 |
| 变更文件没有设计覆盖 | 报告 SHA 和缺失路径 |
| 引用或符号在 revision 不存在 | 报告 revision、路径和符号 |
| 正文仍含执行证据结构 | 通过类型、校验和渲染测试阻止 |
| 旧 SHA 文件或孤儿仍存在 | checker 报告具体路径并非零退出 |
| 索引链接失效 | 链接检查失败，不提交完成结论 |
| 重复生成产生 diff | 视为命名或渲染不确定，停止交付 |

错误信息不得输出疑似凭据内容，也不得用通用正文替代失败记录。

## 9. 验收与测试设计

以下是本次实现的验收标准，不是历史 commit 的执行记录。

### 9.1 命名单元测试

- 从带时区的 commit date 提取正确自然日。
- 接受合法 slug，拒绝空值、大写、空格、斜线和前导/尾随连字符。
- 同日同 slug 依次生成无序号、`-02`、`-03`。
- 同一记录生成相同 basename 的 SPEC 和 PLAN。
- 不同日期可以使用相同 slug。
- 最终路径冲突会失败，重复运行顺序稳定。
- `self` 路径保持固定。

### 9.2 内容与渲染测试

- SPEC 不包含“验证证据”或历史执行结果表。
- PLAN 包含“验收顺序”，且不输出执行通过声明。
- 验收标准、设计引用、回溯说明和文件级步骤仍然保留。
- frontmatter 的 SHA 与记录一致，索引路径与实际文件一致。
- 缺少 slug、旧证据字段、旧 fallback 和复制正文均触发失败。

### 9.3 全量迁移验收

- 仅按设计确认时的 94 个 commit 与 `self` 计算时为 190 份 SPEC/PLAN；实际迁移必须按当前 Git 清单动态计算，并额外覆盖设计评审提交。
- 每个 commit 恰好对应一份 SPEC 和一份 PLAN，没有遗漏或重复。
- 所有文件名符合日期+功能格式，所有同日序号符合历史顺序。
- 旧 SHA 命名文件、孤儿文件和仓库内旧链接为零。
- `INDEX.md` 与 JSON 索引中的 SHA、slug 和路径相互一致。
- 逐份核对日期、slug 和 commit 映射，并抽查大型快照、功能、CI、rename、状态更新和 finalization 文档的正文语义。

### 9.4 工程验证命令

```bash
bun test tests/commitDocs.test.ts
bun run docs:generate -- --next
bun run docs:check -- --next
bun run typecheck
bun test
bun run build
git diff --check
```

重复执行生成命令后，工作树不得出现额外 diff。提交后再以默认 head 模式运行只读检查，验证清单衔接和幂等性。

## 10. 完成定义

只有同时满足以下条件才算完成：

- 全部基线 commit 的 SPEC/PLAN 已迁移为日期+功能命名。
- 每份文档保留实质设计和文件级实施内容，且不再包含历史执行结果。
- 结构化记录、渲染器、索引、政策、模板和测试采用同一契约。
- 自动检查、全量工程验证和人工语义核对均完成。
- 没有旧文件、孤儿、断链、占位正文或不确定生成结果。

本设计不要求历史验证环境可用，也不把文档结构检查表述为产品功能或外部协议已经得到验证。
