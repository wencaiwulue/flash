# 全量子系统设计文档完整性与一致性审查设计

## 1. 问题与约束

仓库已有 68 份注册子系统 spec、coverage YAML 和结构校验器，但结构完整不等于语义完整。以 `context-compaction` 和 `memory` 为例，两份文档都包含详细接口、状态、流程和失败语义，却仍为 `draft`；其中还存在测试缺口、跨系统引用、全局状态和恢复边界等待复核事项。仅有九章正文、coverage 或第 9 章建议，不能证明文档已经准确覆盖真实实现，也不能证明各 spec 组合后的契约一致。

本次审查需要同时回答四个问题：

1. 每份 spec 是否准确、完整地描述当前实现，而非只覆盖主要成功路径。
2. spec 之间共享的消息、状态、持久化、恢复和功能门契约是否一致。
3. 当前实现和文档是否与上游 Claude Code 对齐；偏离是否有明确契约依据。
4. 测试、mock、离线检查和 live 验证分别能证明什么，哪些结论仍未验证。

### 用户确认的范围与方法

- 审查全部 68 个注册子系统，并按 manifest 的 batch 0–7 分批深审。
- internal、experimental、feature-gated 能力与 external 能力采用同等审查深度。
- 同时以当前源码和上游证据为基准，区分当前行为、实现缺陷、上游偏离和可选改进。
- 采用“批次纵向深审 + 横向契约复审”；先提交审查报告，经用户确认后再分批修订文档。
- 本轮不修改产品实现，不直接重写 68 份 spec，不批量改变 `draft` 状态。

### 文档范围

- **深审对象**：manifest 注册的 68 份子系统 spec、对应 coverage groups、源码与测试证据。
- **整体一致性对象**：`docs/ARCHITECTURE.md`、`docs/architecture/INDEX.md`、`docs/COMMIT_DOCS.md`、`docs/STATUS.md`、未注册的工程设计 spec，以及与子系统行为相关的外部 stubs 契约。
- **历史文档边界**：`docs/RELEASE.md` 和历史验证记录用于追溯证据，不改写历史结果；发现其与当前状态冲突时，以当前源码和新验证为准记录问题。
- 未注册 spec 不为了凑数加入子系统 coverage；功能子系统与工程改造的登记规则继续遵循 `docs/COMMIT_DOCS.md` 和 flash-coding 工程约束。本审查方案属于工程改造，不登记 manifest，也不新增 coverage。

### 证据与环境约束

- 上游证据按“官方文档 → 本机上游二进制 `strings` → 本仓库 external-stubs 契约与既有 spec”的顺序收集；行为冲突时按项目规则优先采用可定位的二进制证据。
- 上游文档、二进制和本仓库可能处于不同版本。所有证据必须记录版本、路径或 URL、获取日期及其能证明的边界。
- 私有服务、Cloud、桌面、SSH、OAuth 等环境不可用，不妨碍审查文档是否诚实描述证据边界，但不能据此判定 live 能力通过。
- 测试存在不等于测试通过，mock 不等于 live；源码存在不等于 external build 可用，disabled/stub 不等于功能已实现。
- 审查期间以固定仓库 commit 为基线。源码变化后，受影响条目必须重新核对。

## 2. 设计理由与备选方案

| 决策 | 实际机制 | 为什么采用 | 备选方案及不采用原因 | 代价 | 证据 |
|---|---|---|---|---|---|
| 按 batch 纵向深审，再做横向契约复审 | 每批完成 spec、源码、测试和上游证据闭环；最后跨 batch 对账 | 单个子系统能形成完整结论，跨层问题又不会因分批而丢失 | 仅横向逐章扫描会反复读取同一文件，且很晚才能得到单个子系统结论；仅纵向审查会漏掉跨 spec 矛盾 | 需要统一问题 ID、主责归属和跨批索引 | 用户已确认；manifest batch 0–7；`docs/architecture/coverage/manifest.yaml` |
| 先报告、后分批修订 | 审查阶段只生成证据和缺口；用户确认后再写整改 spec/plan | 避免未审先改，也避免把设计推断直接写回权威文档 | 边审边改会让报告基线持续漂移，整体结论较晚才稳定 | 需要维护一轮独立审查产物 | 用户已确认；`docs/COMMIT_DOCS.md` 要求逐功能评审 |
| 文档完整性与能力验证分开判定 | “描述准确且证据边界完整”与“live 能力已验证”使用不同结论字段 | 私有依赖不可用时仍可确认文档质量，且不会把未验证能力误报为通过 | 合并为一个通过状态会迫使审查者在证据不足时二选一，产生虚假结论 | 报告字段更多 | `docs/ARCHITECTURE.md` feature boundaries；`docs/COMMIT_DOCS.md` 证据边界规则 |
| 统一发现记录和唯一主责 | 每条发现包含类别、证据、影响、主责与关联 spec；跨域只引用同一 ID | 避免同一问题在多份 spec 重复整改，或无人拥有跨层问题 | 每份 spec 独立列问题会重复计数并产生冲突修复 | 需要去重和跨批追踪 | 既有 `design-docs-consistency` 计划已采用唯一主责原则 |
| 所有关键主张均复核，高优先级发现二次独立复核 | 普通发现由审查者回到源码/契约；P0/P1 和上游偏离再由独立复核者尝试反驳 | 全量同等审查需要完整证据；高影响结论还需要降低误报 | 只抽查无法支撑“全部子系统同等深度”；所有条目多人复核成本过高 | 高优先级结论增加一轮复核成本 | 用户选择内部能力同等验收；现有文档政策明确自动检查不能替代语义评审 |
| 横向复审以真实生命周期为单位 | context、memory、session、SDK 等沿端到端数据流对账 | 每份 spec 单独正确并不保证组合后的身份链、状态与恢复语义正确 | 只检查互链和名称无法发现投影、持久化或清理语义冲突 | 需要跨多个 coverage 主责读取文件，但不重复归属 | `docs/superpowers/specs/2026-11-12-context-compaction-design.md` §4.5、§8；`memory` spec §4.6、§8 |

## 3. 目标与非目标

### 3.1 目标

- 为 68 个注册子系统和全部 coverage groups 建立可追踪的审查结论。
- 对关键接口、状态、控制流、持久化、恢复、失败、安全和测试主张进行源码级核对。
- 收集上游文档、本机二进制和本仓库契约证据，明确上游一致、上游偏离或上游未确认。
- 建立跨子系统契约矩阵，重点覆盖 context 与 memory 的完整生命周期。
- 形成可分批整改的总报告和 batch 报告，所有发现可定位、可去重、可复核。
- 分开统计文档缺口、已证实实现问题、上游偏离、验证缺口和可选改进。
- 对报告自身设置完成门禁，未完成的条目不得以“全面”结论掩盖。

### 3.2 非目标

- 不在本轮修改产品源码、修复实现缺陷或添加产品测试。
- 不在审查报告中直接完成 68 份 spec 的改写。
- 不把批准审查报告等同于批准各子系统 spec，不批量将状态改为 `approved`。
- 不承诺访问或兼容无法获得的私有协议与服务。
- 不将上游未提及视为上游不存在，也不将静态推断写成实测结果。
- 不为了自动检查而引入第二套文档体系、文件归属或状态来源。

## 4. 设计明细

### 4.1 审查产物与目录

审查执行阶段使用以下产物；本设计提交时不预建空报告：

```text
docs/status/design-docs-completeness-audit/
  README.md                 # 总矩阵、统计、整改顺序、完成状态
  batch-0.md ... batch-7.md # 逐 spec、逐 coverage group 的证据与发现
  cross-subsystem.md        # 跨系统契约矩阵和关联发现
```

报告属于带基线日期和版本的验证记录，不把历史执行结果写回回溯性设计 spec。若后续形成当前状态摘要，再在 `docs/STATUS.md` 中链接总报告；不改写历史 RELEASE 或旧验证记录。

总矩阵至少包含：

| 字段 | 含义 |
|---|---|
| spec ID / batch | 与 manifest 一致的稳定身份和批次 |
| coverage groups | 已审查数 / 总数；`N/A` 必须附理由 |
| 文档完整性 | complete / gaps / blocked / open |
| 当前实现一致性 | consistent / mismatches / open |
| 上游一致性 | aligned / deviation / unconfirmed / open |
| 验证状态 | live / offline-or-mock / unverified / mixed，并附边界 |
| 发现计数 | 按类别与 P0–P3 分列，不把不同类别混成单一严重度 |
| 主报告链接 | 指向对应 batch 章节和跨系统问题 |

### 4.2 单子系统审查面

每份 spec 按同一检查模型审查，九章结构只作为导航，不能替代以下语义问题：

1. **职责与边界**：上游调用方、下游副作用、非目标；CLI/SDK、internal/external、bundled/source、offline/live 差异。
2. **公共契约**：真实入口、参数、返回类型、消息形状、异步完成条件和副作用；不能只列函数名。
3. **状态与生命周期**：状态所有者、共享/隔离、重置、并发、取消、重复清理和进程/会话边界。
4. **数据流与持久化**：正常、短路径、恢复和提前返回；写入等待顺序、部分写入、身份关联和恢复重建。
5. **失败与安全**：错误传播、重试与上限、fallback、权限、敏感数据、路径边界和 feature-disabled 行为。
6. **验收与测试**：第 6 章是否覆盖第 4/5 章关键行为；测试场景能证明什么，缺少哪些直接、集成或 live 证据。
7. **设计理由**：历史动机是否有注释、协议或已评审设计支持；只有代码结构时必须标为设计推断。
8. **上游对齐**：行为、配置、协议和用户可见结果是否与上游证据一致；有意偏离是否由本仓库契约明确声明。
9. **文件语义覆盖**：coverage 中每组文件是否在第 1–8 章获得与其职责相称的解释；不能只靠 YAML 登记声称已覆盖。

### 4.3 发现记录与分类

每条发现使用统一结构：

```text
ID｜主责 spec｜关联 spec｜类别｜严重度｜问题陈述｜
源码证据｜上游证据｜测试证据｜影响｜修订建议｜置信度｜验证边界｜状态
```

类别定义：

| 类别 | 判定条件 |
|---|---|
| 缺失 | 已实现的关键职责、分支、契约或证据边界没有进入对应 spec |
| 事实错误 | spec 对当前源码、配置、协议或测试的陈述可被直接证据否定 |
| 内部矛盾 | 同一 spec 不同章节对同一行为给出不兼容描述 |
| 跨 spec 冲突 | 多份 spec 对共享契约的所有者、顺序、数据或失败语义不一致 |
| 上游偏离 | 可定位的上游证据与本仓库行为不同；还需区分有意偏离与待修正偏离 |
| 证据不足 | 设计理由、测试结论或 live 能力声明超出现有证据能支持的范围 |
| 测试缺口 | 关键行为缺少可观察回归；不自动等同于实现存在缺陷 |
| 可选改进 | 当前文档和行为没有事实错误，但存在有边界的体验、可维护性或设计优化；不冒充缺陷 |

严重度沿用现有规范：P0 只用于有直接证据的安全、数据丢失、核心正确性或协议边界问题；P1 用于有证据的高影响可靠性、生命周期、并发或性能问题；单纯测试缺口和局部可维护性通常为 P2；可选体验与低收益改进为 P3。`设计推断` 不能单独支撑 P0/P1。

一个问题只有一个主责 spec。其他 spec 在关联字段中引用同一 ID；后续整改时也只设一个主实现任务，跨层验收可以关联多个 spec。

### 4.4 每批执行数据流

```text
固定仓库 commit、上游 CLI 版本、证据日期
  ↓
运行 bun scripts/check-design-docs.ts，保存真实退出码和诊断摘要
  ↓
读取本批 manifest 条目、spec、coverage groups 和相关顶层文档
  ↓
逐关键主张核对源码符号、真实控制流、数据结构与功能门
  ↓
核对测试场景、不变量、mock/离线/live 边界
  ↓
收集官方文档、本机二进制 strings、本仓库契约证据
  ↓
记录发现 → 去重 → 确定主责 → 高优先级独立复核
  ↓
输出 batch 报告并更新总矩阵；未完成项保留 open/blocked
  ↓
用户审阅本批报告；审查意见只影响报告，不自动修改子系统 spec
```

批次之间可以并行阅读独立子系统，但总矩阵更新、跨域去重和主责判定必须集中串行完成，防止竞争和重复编号。子代理或自动检索只负责收集候选证据，主审查者必须读取关键源码后才能确认发现。

### 4.5 横向契约复审

全部 batch 完成后，沿真实生命周期进行第二轮对账。横向复审引用各 spec 的主责文件，不重复 coverage 归属。

#### Context 全生命周期

必须回答：

- 模型可见消息投影、UI transcript、SDK 输出和磁盘会话是否被明确区分，各自由谁拥有。
- system prompt、工具定义、附件、CLAUDE.md、记忆和 token 统计如何进入请求，使用哪个有效上下文窗口。
- microcompact、snip、context collapse、autocompact、reactive compact、session memory compact、manual compact 的触发位置、顺序、互斥和 disabled 分支是否一致。
- 压缩前后 tool_use/tool_result 配对、UUID/parentUuid、preserved segment、缓存和 compact boundary 的不变量是否完整。
- 压缩后文件、plan、skills、agents、MCP 指令等工作上下文如何重建，预算和失败路径是什么。
- QueryEngine 数组裁剪、会话持久化、重启恢复、fork、SDK replay 是否使用同一身份链与投影语义。
- prompt-too-long、空摘要、持久化失败、reset 与后台摘要交错时，哪些状态可提交、可重试或必须丢弃。

#### Memory 全生命周期

必须回答：

- auto、team、Session Memory、CLAUDE.md、KAIROS daily log 的所有者、作用域、隐私和生命周期是否清楚。
- 索引加载、按需检索、主代理写入、自动提取、整理、团队同步、删除、失效与缓存刷新是否有完整流程。
- 内存 cursor、磁盘文件和会话恢复如何组合；重启后重复提取、漏提取或旧光标的安全边界是什么。
- Session Memory 与 compact 的调用关系，是否和 `context-compaction` 的触发/禁用条件一致。
- 压缩后哪些记忆重新注入、哪些缓存必须清除，是否可能重复注入或使用过期的 MEMORY.md。
- auto/team 路径、symlink、secret 扫描和写权限是否在读取、权限裁决和实际写入各层一致。
- autoDream、extractMemories、团队 watcher 与主代理并发时，锁、合并、冲突、取消和失败回滚是否闭合。

#### 其他共享契约

- 模块级状态、多会话、forked agent、后台任务、取消与重复清理。
- 消息、附件、任务、权限、设置、压缩元数据和记忆的持久化/恢复组合。
- 源码存在、构建启用、external stub、协议兼容和 live 已验证五种状态的用词一致性。
- CLI、SDK、daemon、远程入口对同一核心能力的所有权和副作用是否一致。

矩阵每一格必须是 `confirmed`、`gap`、`conflict`、`unconfirmed` 或 `N/A（理由）` 之一，并链接证据或发现 ID。

### 4.6 证据冲突与未完成状态

| 场景 | 审查处理 | 禁止结论 |
|---|---|---|
| 官方文档与二进制冲突 | 记录双方版本和证据；按项目规则优先采用可定位的二进制行为 | 静默选择较符合现有实现的描述 |
| 二进制无法提取目标逻辑 | 标记 `上游未确认`，保留文档证据及其局限 | 将“未找到”写成“上游不存在” |
| 私有 live 环境不可用 | 标记 `blocked` 或 `unverified`，审查文档是否如实披露 | 用 mock、build 或测试文件存在宣称 live 通过 |
| spec、源码、测试互相冲突 | 分别记录观察结果，建立主问题并独立复核高影响结论 | 为保持文档一致而忽略反证 |
| 审查中源码变化 | 固定基线；重新核对受影响条目并记录新 commit | 混合不同版本的证据得出单一结论 |
| 单项无法完成 | 保持 `open`，列入总报告阻塞项 | 以大多数条目完成推断全量完成 |
| 跨 spec 重复问题 | 合并 ID、唯一主责、其他位置引用 | 重复计数或创建互不关联的整改任务 |

### 4.7 后续整改接口

审查完成后，先由用户确认总报告及整改顺序，再按以下原则分批：

1. P0/P1 的已证实实现问题与文档事实错误优先；文档修复和产品修复分别走自己的 spec/plan。
2. 跨系统问题由主责 spec 牵头，关联 spec 只修改自己的调用边界，不复制整段设计。
3. 单纯证据不足先补证据，不直接改写为肯定或否定结论。
4. 有意上游偏离必须在本仓库契约或 spec 决策表中明确记录；非有意偏离按上游语义优先。
5. 每次文档修订运行 `bun scripts/check-design-docs.ts`；涉及代码时按变更范围运行测试，并在完成后运行 `bun run test`、`bun run typecheck` 和 `bun run build`。
6. 子系统 spec 只有在正文修订并经用户审阅后才能改为 `approved`。

## 5. 失败语义与风险

| 风险 | 触发场景 | 缓解与验收 |
|---|---|---|
| 以篇幅代替完整性 | spec 很长但仍遗漏关键投影、恢复或并发路径 | 使用逐 coverage group 和横向生命周期矩阵；长度不进入完成判定 |
| 证据外观化 | 只贴文件路径或测试名，未说明证明的行为和边界 | 发现记录必须包含符号、场景、不变量和证据边界 |
| 上游误配版本 | 用不同版本文档或二进制直接否定本仓库行为 | 固定版本、日期与证据片段；无法确认时保持 unconfirmed |
| 审查者确认偏误 | 为已有 spec 寻找支持，忽略反例 | P0/P1 和上游偏离进行独立反驳式复核 |
| 跨域问题重复或漏管 | context/memory/session 各自记录不同版本的问题 | 集中去重、唯一主责、关联 ID 和跨系统矩阵 |
| 私有环境形成虚假完成 | 无法运行 live 却仍标记全部验证完成 | 文档完整性与能力验证分列；阻塞项必须进入总报告 |
| 审查过程污染权威状态 | 未确认的推断直接写回 spec 或 STATUS | 本轮只写审查报告；用户确认后才分批整改 |

## 6. 现状验收标准

1. **范围闭合**：68 个注册 spec 和全部 coverage group 均有结论；未注册工程 spec 与顶层文档完成整体一致性检查；所有 `N/A` 有明确理由。
2. **证据闭合**：每条发现均有可定位源码、上游、测试或契约证据；P0/P1 与上游偏离完成第二次独立复核。
3. **context 闭合**：§4.5 的模型投影、压缩顺序、身份链、重建、恢复和失败问题均有结论或显式缺口。
4. **memory 闭合**：§4.5 的记忆类型、加载、写入、提取、整理、同步、失效、恢复、安全和并发问题均有结论或显式缺口。
5. **跨域闭合**：横向矩阵无空白单元格；跨域发现唯一主责且被相关 batch 报告引用。
6. **结论诚实**：文档完整性、实现正确性、上游一致性和 live 验证状态分别统计，没有将 mock/offline 升级为 live。
7. **无隐性未完成**：所有 `open`、`blocked`、`unconfirmed` 均进入总报告；存在 `open` 时不得声明全量审查完成，存在 `blocked` 或 `unconfirmed` 时不得声明相应证据链已经闭合。
8. **结构验证**：运行 `bun scripts/check-design-docs.ts` 并记录真实退出码；报告内本地链接有效。若为争议补充运行测试，记录真实命令、退出码和证据边界。
9. **整改可执行**：总报告按类别和优先级给出明确批次，每项后续工作有唯一主责和可观察验收条件。
10. **用户门禁**：总报告经用户审阅后才开始分批修订；报告批准不自动改变任何子系统 spec 的状态。
