# 实施计划：Document every commit with specs and plans

> 本文按实际代码依赖重建实施顺序，用于说明怎样完成该提交；不伪称是历史提交当时保存的计划。

## 目标与前置条件

该提交建立生成器、self 约定和 checker 来解决覆盖与 SHA 自引用，但内容层主要仍是 DETAILS 的四类短句、通用 fallback 和固定三步 PLAN；生命周期层又在生成时枚举包含当前 HEAD 的全部 commits，同时额外加入 self，导致提交前后预期清单不一致。

- 确认当时有 41 个祖先和一项未提交文档工作，并理解当前 commit 无法在自己的树内预先知道最终 SHA。

## 复用与兼容处理

### 复用现有实现

- 复用 git metadata、现有 docs/STATUS/RELEASE、Bun 脚本和基础 CI，不引入新的文档服务。

### 兼容、迁移与生命周期

- self 保持当前工作的稳定链接，旧全局 STATUS/RELEASE 继续存在；但动态 HEAD 清单使已提交生成结果不能稳定复现。

## 文件级实施步骤

### 1. 实现提交元数据与内容模型

在 document-commits.ts 定义 Commit/Details、Git 查询、DETAILS、statusFor 和 self 环境输入，先形成可批量读取的历史清单。

涉及位置：`scripts/document-commits.ts`

### 2. 生成 SPEC、PLAN 与索引

实现 specFor/planFor 及 INDEX/status JSON 投影，同时加入 fallback 和默认 PLAN；批量产出 41 个历史 SHA pairs、self pair 与两个索引；两个 template.md 则作为静态文件单独加入，不在 buildCommitDocuments 的输出集合中。

涉及位置：`scripts/document-commits.ts`、`docs/specs/`、`docs/plans/`、`docs/INDEX.md`、`docs/status/index.json`

### 3. 加入只读 checker 和命令入口

让 checker 复用生成器比较实际文件，在 package.json 注册 docs:generate/docs:check。

涉及位置：`scripts/check-commit-docs.ts`、`package.json`

### 4. 接入全历史 CI

把 checkout 改为 fetch-depth: 0，并在 typecheck 后运行 checker，确保历史记录可被完整枚举。

涉及位置：`.github/workflows/ci.yml`

### 5. 写政策与验证声明

在 COMMIT_DOCS 记录 self 和维护步骤，在 STATUS/RELEASE 写入 41 pairs 与检查声明；此处还应发现 HEAD/self 和正文深度问题，但原提交未完成。

涉及位置：`docs/COMMIT_DOCS.md`、`docs/STATUS.md`、`docs/RELEASE.md`

## 风险与处理

- 生成器与 checker 共用同一内容来源会掩盖泛化正文；预提交生成又把上一 HEAD 的视角固化进当前 commit。

## 验证顺序

1. 核对 95 文件和目录计数，运行生成/比较检查，并单独测试提交后 HEAD 新增时是否出现额外 SHA pair；正文还需逐提交语义审查。
