# 实施计划：Design date-based commit documentation

> 本文按实际代码依赖重建实施顺序，用于说明怎样完成该提交；不伪称是历史提交当时保存的计划。

## 目标与前置条件

下一阶段的文档迁移同时涉及命名、同日冲突、完整 SHA 映射、证据移除、旧链接和生成/检查语义。如果没有独立设计就批量改写九十余个提交的记录，容易丢失已有设计内容、混淆 self 与历史身份，或把历史执行结果继续复制到目标格式。

- c69c271 的结构化记录、实质 SPEC/PLAN 和只读 CI 政策已经存在，迁移以保留这些设计内容为前提。

## 复用与兼容处理

### 复用现有实现

- 复用现有 self/head/next 语义、完整 SHA 记录身份、Bun 生成与检查入口，避免另建平行文档系统。

### 兼容、迁移与生命周期

- 内部 records 仍按 short SHA 加载，完整 SHA 是稳定身份；只有交付 SPEC/PLAN 路径改为日期加功能名。
- self 继续承接未提交工作，新历史记录必须先固化当前 self 和已落地设计提交。

## 文件级实施步骤

### 1. 评审命名与迁移契约

把目标、非目标、数据流、记录与渲染变化、迁移和验收写成独立设计，明确本提交不执行迁移。

涉及位置：`docs/superpowers/specs/2026-11-11-date-based-commit-design-docs-design.md`

## 风险与处理

- 同日冲突和批量 rename 容易产生覆盖、孤儿与断链，设计要求确定性序号、统一命名和只读检查。
- 删除证据字段可能误删实现范围信息，迁移需区分执行结果与仍可保留的设计行为。

## 验证顺序

1. 后续实现先测试日期、slug、冲突、内容和渲染，再执行全量 next 生成与只读检查。
2. 核对动态 Git 清单、每提交一对文档、索引链接、旧文件清零和重复生成幂等。
3. 本提交仅核对设计文件和完成定义，不声明后续命令已执行。
